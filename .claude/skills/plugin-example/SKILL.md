# Plugin example YAML skill

This skill is for first-party Kong plugins only: ones shipped and maintained by Kong
(`publisher: kong-inc` in `index.md`), for example `proxy-cache`, `acl`, `basic-auth`,
`rate-limiting-advanced`. If the plugin's publisher is a vendor, not Kong, stop and use the
third-party-plugin skill instead, even for a small edit to one example file. Third-party
examples follow different conventions (see that skill's `references/example-template.md`).
Mixing the two conventions produces inconsistent output.

This skill covers writing a single `app/_kong_plugins/<plugin-slug>/examples/<name>.yaml`
file: the structured example blocks that render on a plugin's doc page and its
`/plugins/<slug>/examples/<name>/` standalone page.

Read `references/example-template.md` for the full annotated field reference before writing.
It documents every field, what's required vs optional, and the description/extended_description
rule in detail. This file covers the workflow and the things people get wrong.

---

## Step 1: Read the plugin's actual schema for the target version

Never guess field names, types, defaults, or enum values from memory or from the plugin's
prose in `index.md`. **Always ignore `reference.md` and `changelog.json` in a plugin's
directory.** Both are autogenerated and must never be read as a source of truth or edited
by hand.

The source of truth is the versioned JSON Schema:

```
app/_schemas/gateway/plugins/<version>/<PluginName>.json
```

For example, the Proxy Cache plugin's 3.16 schema is
`app/_schemas/gateway/plugins/3.16/ProxyCache.json`. `<PluginName>` is PascalCase and does
not always match the plugin slug exactly, so list the directory for the target version if
the name isn't obvious.

If the example demonstrates a field newer than the plugin's baseline `min_version`, confirm
the field actually exists in the schema version you're targeting, and note which version
directory it first appears in. That version becomes the example's `min_version` (see Step 3).

If a field has an `enum`, use one of the enum's actual values, not something plausible-sounding.
If a field is a nested `record`/`object`, mirror the nesting exactly as declared in the schema.

## Step 2: Decide description vs extended_description

- `description` is required: one line, one sentence, no markdown. It's used for search
  metadata and is the fallback rendered on the page.
- `extended_description` is optional. If present, it fully replaces `description` on the
  rendered page. **It must restate everything `description` says, then add detail on top.**
  Never write it as a separate, additive block. If you do, the reader who only sees
  `extended_description` misses whatever unique content you left only in `description`.
- Default to `description` alone for a simple example. Add `extended_description` only when
  there's real extra context to give, such as why this config choice, what trade-off it
  implies, or what topology it assumes.

## Step 3: Always set min_version explicitly

Every example file must set `min_version.gateway`. Never omit it, and never assume it will
inherit the plugin's own baseline version from `index.md`. Always write it explicitly on
the example itself, even when it happens to equal the plugin's baseline.

Figure out the right value the same way you'd figure out any other field: by checking what
the example actually demonstrates against the schema.

- If every field the example sets has existed since the plugin's baseline, use that
  baseline version.
- If the example demonstrates a field or behavior newer than the baseline, use that field's
  introduction version instead. This is the common case when writing an example specifically
  to showcase a newly added field. **Ask the user for the version if it's not already
  obvious from the schema directory you read it from in Step 1.** Don't guess.

## Step 4: Draft the file

Read `references/example-template.md` now for the field-by-field reference (naming,
`weight`, `requirements`, `variables`, `config`, `tools`) and follow it. The two things
worth flagging up front, because they're the easiest to get wrong on autopilot:

- `weight` controls display order and **higher sorts first**. Don't assume ascending order.
- `tools` should reflect what this specific example can actually be configured with, not
  a copy-pasted full list of `deck`, `admin-api`, `konnect-api`, `kic`, `terraform`. Check
  whether the example's strategy or feature is genuinely unsupported on any of those before
  including them all.

## Step 5: Update the overview page's use case table, if one exists

Check the plugin's `index.md` for a use case table linking to its examples: a `{% table %}`
block whose first column links to `/plugins/<slug>/examples/<example-slug>/` paths. Not
every plugin has one. Some only prose-link examples inline, or not at all.

If the table exists, add a new row for the example you just wrote, matching its existing
column structure and tone. For example (from `json-threat-protection/index.md`):

```yaml
rows:
  - usecase: "[Cache by Principal](/plugins/proxy-cache/examples/cache-by-principal/)"
    description: Use the authenticated Principal's UUID, instead of the Consumer's UUID, to compose the cache key.
```

If the row documents a feature newer than the table's other rows, add the `{% new_in %}`
tag inline next to the link text, matching the version you set in `min_version.gateway`.

If no use case table exists, don't invent one just to link a single new example. That's a
larger structural change than this skill covers. See Step 6 for the broader question of
whether the overview page needs new content at all.

## Step 6: Check whether the overview page needs a new section

A new example sometimes documents a feature substantial enough that the overview page's
prose should explain it too, not just link an example for it, for instance a new field that
changes core behavior (like a cache key composition rule), not a minor variant of an
existing pattern.

Before finishing, ask the user: does `index.md` need a new or updated section to explain
this feature, beyond the use case table row and the example itself? Don't add one unprompted.
This skill's scope is the example YAML file. Overview content is a separate editorial call
the user should make deliberately.

## Step 7: Sanity-check before finishing

- Does every `config` field in this example exist in the schema you read in Step 1, with
  the right type and nesting?
- Does `extended_description`, if present, still cover everything `description` said?
- Is `min_version.gateway` set explicitly, and does it point at the right version (the field's
  introduction version, not blindly the plugin's baseline)?
- Does `weight` correctly rank this example relative to any siblings already in the same
  `examples/` directory?
- If a use case table exists on the overview page, did you add a row for this example?
- Did you ask the user whether the overview page needs a new documentation section?
