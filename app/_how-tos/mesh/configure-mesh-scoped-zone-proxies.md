`kong-air-mesh` carries passenger PII, so its cross-zone traffic must present a verifiable mTLS identity and remain independently observable and governable. Mesh-scoped zone proxies give the mesh a dedicated ingress and egress for that traffic:

Each mesh-scoped proxy is a `Dataplane` inside the mesh, the same resource kind used for application sidecars. Policies can therefore select a zone proxy by its labels and listener role.

## Give your mesh its own zone proxies

Add a `meshes:` entry to each zone control plane's Helm values, name the mesh, and enable its `ingress` and `egress`. This gives `kong-air-mesh` its own ingress and egress Deployment, each with its own Service and ServiceAccount. For the Helm values and upgrade commands, see [Deploy mesh-scoped zone proxies](/mesh/zone-proxies/).

## Confirm the proxies belong to your mesh

Once the pods are `Running`, you can see that the zone proxies are now first-class members of `kong-air-mesh`, each one a `Dataplane` carrying the mesh label.

1. Confirm the zone proxy pods are running:

   ```bash
   kubectl get pods -n kong-mesh-system \
     -l "kuma.io/mesh=kong-air-mesh"
   ```

1. List the `Dataplane` resources the control plane holds for the mesh:

   ```bash
   kongctl get mesh dataplanes --control-plane-name "$MESH_CP" --mesh kong-air-mesh
   ```

   {:.info}
   > A zone proxy's `Dataplane` is generated by the control plane, not applied as a Kubernetes object, so `kubectl get dataplanes` does not return it. Query the control plane instead.

1. Inspect the zone ingress entry. Its name is the pod name followed by the namespace:

   ```bash
   kongctl get mesh dataplanes kong-mesh-kong-air-mesh-ingress-77499bbc58-kkssn.kong-mesh-system \
     --control-plane-name "$MESH_CP" --mesh kong-air-mesh -o yaml
   ```

   A zone ingress `Dataplane` looks like this, note it belongs to `kong-air-mesh` and exposes a `ZoneIngress` listener:

   ```yaml
   kri: kri_dp_kong-air-mesh_zone1_kong-mesh-system_kong-mesh-kong-air-mesh-ingress-77499bbc58-kkssn_
   labels:
     k8s.kuma.io/service-account: kong-mesh-kong-air-mesh-ingress
     k8s.kuma.io/zone-proxy-type: ingress
     kuma.io/listener-zoneingress: enabled
     kuma.io/mesh: kong-air-mesh
     kuma.io/origin: zone
     kuma.io/zone: zone1
   mesh: kong-air-mesh
   name: kong-mesh-kong-air-mesh-ingress-77499bbc58-kkssn.kong-mesh-system
   networking:
     address: 10.42.0.30
     admin:
       port: 9901
     listeners:
       - address: 10.42.0.30
         name: "10001"
         port: 10001
         type: ZoneIngress
   ```
   {:.no-copy-code}

   {:.info}
   > The listener `name` (here `"10001"`) is what you use in `sectionName` to target one specific listener. For Helm-deployed proxies with no named ports it defaults to the port number as a string, `"10001"` for zone ingress and `"10002"` for zone egress.
   >
   > A healthy listener reports no `state` field. `Ready` is the default value, so it only appears in the output when the listener is `NotReady`.

1. Check the `MeshZoneAddress` resources that advertise where this mesh's ingresses can be reached:

   ```bash
   kongctl get mesh meshzoneaddresses --control-plane-name "$MESH_CP" --mesh kong-air-mesh -o yaml
   ```

   ```yaml
   items:
     - kri: kri_mza_kong-air-mesh_zone1_kong-mesh-system_kong-mesh-kong-air-mesh-ingress_
       labels:
         kuma.io/mesh: kong-air-mesh
         kuma.io/origin: zone
         kuma.io/zone: zone1
       mesh: kong-air-mesh
       name: kong-mesh-kong-air-mesh-ingress.kong-mesh-system
       spec:
         address: 203.0.113.42  # public LoadBalancer IP
         port: 10001
       type: MeshZoneAddress
   total: 1
   ```
   {:.no-copy-code}

   Each zone publishes its own entry and receives the other zones' entries over KDS, so `total` grows with the deployment. Check the labels to tell them apart: `kuma.io/origin: zone` marks the entry this zone published, and `kuma.io/origin: global` marks one synced in from the peer named by `kuma.io/zone`.

If you scale the zone ingress to zero, its `MeshZoneAddress` is withdrawn automatically, so other zones stop routing to a dead endpoint.

## Give cross-zone traffic a verifiable identity

The compliance requirement that started this needs no extra resource. `kong-air-identity` from [Get started with your first policy](/mesh/get-started-with-your-first-policy/) selects every `Dataplane` in the mesh, and the zone proxies are `Dataplane` resources in the mesh, so they are already covered:

```yaml
  selector:
    dataplane:
      matchLabels:
        kuma.io/mesh: kong-air-mesh
```
{:.no-copy-code}

Confirm the ingress received a certificate from that identity:

```sh
INGRESS_POD=$(kubectl get pod -n {{site.mesh_namespace}} \
  -l "kuma.io/mesh=kong-air-mesh,k8s.kuma.io/zone-proxy-type=ingress" \
  -o jsonpath='{.items[0].metadata.name}')
kubectl get dataplaneinsight "$INGRESS_POD" -n {{site.mesh_namespace}} \
  -o jsonpath='{.status.mTLS.issuedBackend}{"\n"}'
```

Expected output:

```text
kri_mid_kong-air-mesh_zone1_kong-mesh-system_kong-air-identity_
```
{:.no-copy-code}

Because the proxy runs under its own ServiceAccount, it presents a SPIFFE ID distinct from any application workload, built from the same `spiffeID.path` template:

```text
spiffe://kong-air-mesh.zone1.mesh.local/ns/kong-mesh-system/sa/kong-mesh-kong-air-mesh-ingress
```
{:.no-copy-code}

That is the identity a peer zone sees on cross-zone traffic, and the value a `MeshTrafficPermission` in the peer zone matches on.

## Target the proxies with policy

Because the proxies are `Dataplane` resources in `kong-air-mesh`, supported mesh policies can target them. Select them with `targetRef.kind: Dataplane` and the `kuma.io/listener-zoneingress: enabled` or `kuma.io/listener-zoneegress: enabled` labels, adding a `sectionName` to target one specific listener by name.

Scope metrics to this mesh's ingress:

```yaml
apiVersion: kuma.io/v1alpha1
kind: MeshMetric
metadata:
  name: kong-air-ingress-metrics
  namespace: {{site.mesh_namespace}}
  labels:
    kuma.io/mesh: kong-air-mesh
    kuma.io/origin: zone
spec:
  targetRef:
    kind: Dataplane
    labels:
      kuma.io/listener-zoneingress: enabled
    sectionName: "10001"
  default:
    sidecar:
      includeUnused: false
    backends:
      - type: Prometheus
        prometheus:
          port: 5670
          path: /metrics
```

The same selector shape works for `MeshTimeout`, `MeshAccessLog`, and `MeshRateLimit`. Omit `sectionName` to cover every listener on the proxy.

## Govern what leaves through the egress

A mesh-scoped zone egress is **deny-all** by default for `MeshExternalService` traffic. The control plane installs an RBAC filter on each `MeshExternalService` filter chain, and that filter ends in a deny, so nothing reaches an external destination until you say so. Open individual destinations with `MeshTrafficPermission` targeting the zone-egress `Dataplane`:

```yaml
apiVersion: kuma.io/v1alpha1
kind: MeshTrafficPermission
metadata:
  name: flight-db-access
  namespace: {{site.mesh_namespace}}
  labels:
    kuma.io/mesh: kong-air-mesh
    kuma.io/origin: zone
spec:
  targetRef:
    kind: Dataplane
    labels:
      kuma.io/listener-zoneegress: enabled
  rules:
    - default:
        allow:
          - spiffeID:
              type: Exact
              value: spiffe://kong-air-mesh.zone1.mesh.local/ns/kong-air-production/sa/flight-control
            sni:
              type: Exact
              value: sni.extsvc.kong-air-mesh.zone1.{{site.mesh_namespace}}.flight-db.5432
```

An entry allows a connection only when the caller's SPIFFE ID and the destination SNI both match. For how to derive each value, see [Manage external services with MeshExternalService](/mesh/manage-external-services-with-meshexternalservice/).

{:.info}
> Earlier versions expressed this as a mesh-wide toggle, `routing.defaultForbidMeshExternalServiceAccess`. That field is gone from the `Mesh` schema in 3.0, and a mesh-scoped zone egress is closed by default with no toggle to set. `MeshTrafficPermission` is now the only way to express external service access.

The RBAC filter sits at the network layer for TCP destinations and inside the HTTP connection manager for HTTP ones, so a denied request either has its connection closed or receives a `403`. Either way the decision is countable: the egress publishes `rbac.allowed` and `rbac.denied` counters per destination, which is the signal to check when a request fails and you are not sure whether the perimeter or the route is responsible.

## Validate

1. Confirm the mesh-scoped ingress and egress pods for `kong-air-mesh` are `Running`:

   ```sh
   kubectl get pods -n kong-mesh-system -l "kuma.io/mesh=kong-air-mesh"
   ```

   Expected output, both pods `2/2` and `Running`. Each zone proxy pod runs the proxy container alongside a `kuma-sidecar`:

   ```text
   NAME                                               READY   STATUS    RESTARTS   AGE
   kong-mesh-kong-air-mesh-egress-5d8f7c9b6d-p4x2q    2/2     Running   0          2m
   kong-mesh-kong-air-mesh-ingress-77499bbc58-kkssn   2/2     Running   0          2m
   ```
   {:.no-copy-code}

1. Confirm each proxy is attributed to the right mesh and has the role you expect:

   ```sh
   kubectl get pods -n kong-mesh-system -l kuma.io/mesh=kong-air-mesh \
     -o custom-columns='NAME:.metadata.name,MESH:.metadata.labels.kuma\.io/mesh,TYPE:.metadata.labels.k8s\.kuma\.io/zone-proxy-type'
   ```

   Expected output, one ingress and one egress for the mesh:

   ```text
   NAME                                               MESH            TYPE
   kong-mesh-kong-air-mesh-egress-5d8f7c9b6d-p4x2q    kong-air-mesh   egress
   kong-mesh-kong-air-mesh-ingress-77499bbc58-kkssn   kong-air-mesh   ingress
   ```
   {:.no-copy-code}

   {:.info}
   > These are pods, which is why `kubectl` can see them. The matching `Dataplane` resources are generated by the control plane rather than applied as Kubernetes objects, so `kubectl get dataplanes` returns nothing for them. Use `kongctl get mesh dataplanes --mesh kong-air-mesh` to list them, `kongctl get mesh inspect dataplanes --mesh kong-air-mesh` for the control plane's overview, and `kongctl get mesh inspect dataplane <name> --mesh kong-air-mesh` to see what applies to one.

Together, these confirm the mesh-scoped proxies are healthy and that each one is bound to `kong-air-mesh` by its `kuma.io/mesh` label.
