In [Create a security policy](/mesh/create-a-security-policy/), `flight-control` presented its identity, and `check-in-api` authorized it.
In this guide, you inspect the resources behind that result.
Then you extend the same identity and trust to a second zone.

## Identity, trust, enforcement, and authorization

A request between two Kong Air services succeeds only when all of the following are true:
* The caller presents a certificate with a Secure Production Identity Framework for Everyone (SPIFFE) ID, issued by [`MeshIdentity`](/mesh/policies/meshidentity/).
* The receiver trusts the issuing certificate authority (CA) through a [`MeshTrust`](/mesh/policies/meshtrust/).
* A [`MeshTrafficPermission`](/mesh/policies/meshtrafficpermission/) allows the caller.

When Kong Air adds a second zone, all three must also hold across zones.

## Inspect the identity created in zone1

You created `kong-air-identity` on the `zone1` control plane, in the `{{site.mesh_namespace}}` namespace.
The `kong-air-identity` selector covers every data plane proxy in `kong-air-mesh`, including application sidecars and mesh-scoped zone proxies.

1. Check that `kong-air-identity` initialized.
   `MeshIdentity` reports three conditions, and all three must be `True`:

   ```sh
   kubectl get meshidentity kong-air-identity -n {{site.mesh_namespace}} \
     -o jsonpath='{range .status.conditions[*]}{.type}={.status}{"\n"}{end}'
   ```

   Expected output:

   ```text
   Provider=True
   MeshTrustCreated=True
   Ready=True
   ```
   {:.no-copy-code}

   Each condition reports one part of the setup:
   * `Provider`: The CA is usable.
   * `MeshTrustCreated`: The provider published a `MeshTrust`.
   * `Ready`: The identity can issue certificates.

1. Inspect the `MeshTrust` that the `Bundled` provider created.
   Because `kong-air-identity` sets `meshTrustCreation: Enabled`, the control plane creates a `MeshTrust` with the same name:

   ```sh
   kubectl get meshtrust kong-air-identity -n {{site.mesh_namespace}} \
     -o jsonpath='{.spec.trustDomain}{"\n"}{.spec.caBundles[0].type}{"\n"}'
   ```

   Expected output:

   ```text
   kong-air-mesh.zone1.mesh.local
   Pem
   ```
   {:.no-copy-code}

   The control plane records the resolved trust domain in the `MeshIdentity` `status.trustDomain` field, and the generated `MeshTrust` carries the same domain.
   The `kong-air-identity` resource doesn't set `spec.spiffeID.trustDomain`, so the control plane renders the default template, `{% raw %}{{ .Mesh }}.{{ .Zone }}.mesh.local{% endraw %}`.
   The CA private key stays with the provider.
   The `MeshTrust` contains only the public CA certificate that proxies use to verify peers.

1. Confirm which `MeshIdentity` issued each workload's certificate:

   ```sh
   kubectl get dataplaneinsights -n kong-air-production \
     -o custom-columns='NAME:.metadata.name,ISSUER:.status.mTLS.issuedBackend,EXPIRES:.status.mTLS.certificateExpirationTime'
   ```

   Each `ISSUER` value contains `kong-air-identity`.
   An empty value means that no `MeshIdentity` selector matches that data plane proxy.


## Extend autogenerated identity across zones

When you use the `Bundled` provider with `autogenerate.enabled: true`, each zone control plane generates its own CA.
Each zone also gets its own trust domain:

```text
zone1: kong-air-mesh.zone1.mesh.local
zone2: kong-air-mesh.zone2.mesh.local
```
{:.no-copy-code}

Each zone trusts its own CA.
The zone control plane sends its generated `MeshTrust` to the global control plane over the Kuma Discovery Service (KDS).
The global control plane doesn't send that `MeshTrust` to the other zones.
For cross-zone mTLS to work, you must copy each zone's generated `MeshTrust` into every other zone.

The copied names don't collide on the global control plane, because KDS adds the zone and namespace to the names of synced resources.

You can also create the `MeshTrust` copies on the global control plane, which sends them to every zone.
See [Multi-zone meshes](/mesh/policies/meshidentity/#multi-zone-meshes).

{:.info}
> The Kong Air scenario runs one connected zone, `zone1`, so you can't run the commands in this section yet.
> Use them when you connect a second zone to `kong-air-mesh`, and replace the zone names and `kubectl` contexts with your own.

### Apply the identity in the second zone

After you connect `zone2` to the same global control plane, create the same `kong-air-identity` on the `zone2` control plane.
You can only create a `MeshIdentity` in the system namespace.
In `zone2`, the default trust domain resolves to `kong-air-mesh.zone2.mesh.local`:

```sh
kubectl --context zone2 apply -f - <<'EOF'
apiVersion: kuma.io/v1alpha1
kind: MeshIdentity
metadata:
  name: kong-air-identity
  namespace: {{site.mesh_namespace}}
  labels:
    kuma.io/mesh: kong-air-mesh
spec:
  selector:
    dataplane:
      matchLabels:
        kuma.io/mesh: kong-air-mesh
  provider:
    type: Bundled
    bundled:
      insecureAllowSelfSigned: true
      autogenerate:
        enabled: true
      meshTrustCreation: Enabled
  spiffeID:
    path: /ns/{% raw %}{{ .Namespace }}{% endraw %}/sa/{% raw %}{{ .ServiceAccount }}{% endraw %}
EOF
```

For production, we recommend a managed CA or SPIRE instead of self-signed autogenerated CAs, because you control the CA lifecycle.
See [Providers](/mesh/policies/meshidentity/#providers).
This guide uses autogenerated CAs so you can see and test the trust relationship.

### Copy zone1 trust into zone2

A `MeshTrust` spec holds only a `trustDomain` and a list of `caBundles`, so the copy never includes the CA private key.
Create a `MeshTrust` named `kong-air-mesh-trust-of-zone1` in `zone2`, with the two fields read from the `zone1` `MeshTrust`:

```sh
kubectl --context zone2 apply -f - <<EOF
apiVersion: kuma.io/v1alpha1
kind: MeshTrust
metadata:
  name: kong-air-mesh-trust-of-zone1
  namespace: {{site.mesh_namespace}}
  labels:
    kuma.io/mesh: kong-air-mesh
spec:
  trustDomain: $(kubectl --context zone1 get meshtrust kong-air-identity -n {{site.mesh_namespace}} -o jsonpath='{.spec.trustDomain}')
  caBundles: $(kubectl --context zone1 get meshtrust kong-air-identity -n {{site.mesh_namespace}} -o jsonpath='{.spec.caBundles}')
EOF
```

### Copy zone2 trust into zone1

Create a `MeshTrust` named `kong-air-mesh-trust-of-zone2` in `zone1`, with the two fields read from the `zone2` `MeshTrust`:

```sh
kubectl --context zone1 apply -f - <<EOF
apiVersion: kuma.io/v1alpha1
kind: MeshTrust
metadata:
  name: kong-air-mesh-trust-of-zone2
  namespace: {{site.mesh_namespace}}
  labels:
    kuma.io/mesh: kong-air-mesh
spec:
  trustDomain: $(kubectl --context zone2 get meshtrust kong-air-identity -n {{site.mesh_namespace}} -o jsonpath='{.spec.trustDomain}')
  caBundles: $(kubectl --context zone2 get meshtrust kong-air-identity -n {{site.mesh_namespace}} -o jsonpath='{.spec.caBundles}')
EOF
```

With three or more zones, every zone needs one `MeshTrust` for each other zone whose certificates it accepts.
We recommend that you automate these copies, because the number of copies grows quickly with each new zone.

## Validate trust before routing traffic

1. Confirm that each zone has its own generated `MeshTrust` and the copy from the other zone:

   ```sh
   kubectl --context zone1 get meshtrust -n {{site.mesh_namespace}}
   kubectl --context zone2 get meshtrust -n {{site.mesh_namespace}}
   ```

   The `zone1` output lists `kong-air-identity` and `kong-air-mesh-trust-of-zone2`.
   The `zone2` output lists `kong-air-identity` and `kong-air-mesh-trust-of-zone1`.

1. Confirm that each copied `MeshTrust` holds the other zone's trust domain:

   ```sh
   kubectl --context zone1 get meshtrust kong-air-mesh-trust-of-zone2 \
     -n {{site.mesh_namespace}} -o jsonpath='{.spec.trustDomain}{"\n"}'
   kubectl --context zone2 get meshtrust kong-air-mesh-trust-of-zone1 \
     -n {{site.mesh_namespace}} -o jsonpath='{.spec.trustDomain}{"\n"}'
   ```

   Expected output:

   ```text
   kong-air-mesh.zone2.mesh.local
   kong-air-mesh.zone1.mesh.local
   ```
   {:.no-copy-code}

1. Confirm that the proxies loaded the copied `MeshTrust`.
   A `MeshTrust` can exist in the API before the control plane sends it to the proxies.
   The `DataplaneInsight` resource lists the trusts that each proxy accepts:

   ```sh
   kubectl --context zone1 get dataplaneinsights -n kong-air-production \
     -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.status.mTLS.supportedBackends}{"\n"}{end}'
   ```

   Every line contains two `kri_mtrust_` entries: one for the local identity and one for the copy from the other zone:

   ```text
   check-in-api-654c44bbdb-n55x8	["kri_mtrust_kong-air-mesh_zone1_kong-mesh-system_kong-air-identity_","kri_mtrust_kong-air-mesh_zone1_kong-mesh-system_kong-air-mesh-trust-of-zone2_"]
   ```
   {:.no-copy-code}

   The `ISSUER` check in [Inspect the identity created in zone1](#inspect-the-identity-created-in-zone1) reads the same `DataplaneInsight` resource from the issuing side.

These checks show that proxies in each zone can verify certificates from the other zone.
With identities in both zones and trust in both directions, proxies can now establish cross-zone mTLS.
Next, add `MeshTrafficPermission` rules that allow the SPIFFE IDs from the other zone, and send a request through the mesh-scoped zone proxies to verify it.
