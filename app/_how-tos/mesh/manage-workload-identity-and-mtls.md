The first security scenario proves that `flight-control` can present an authenticated identity and that `check-in-api` can authorize it. This page explains the resources behind that result and the decisions you must make before carrying the same security model into another zone.

## Identity, trust, enforcement, and authorization

Four resources take part in a secured request:

<!-- vale off -->
{% table %}
columns:
  - title: Resource
    key: resource
  - title: Responsibility
    key: responsibility
  - title: Kong Air example
    key: example
rows:
  - resource: "`MeshIdentity`"
    responsibility: "Selects data planes, chooses an identity provider, and defines the SPIFFE ID template."
    example: "Issues a certificate to `flight-control` with its zone, namespace, and service account in the SPIFFE ID."
  - resource: "`MeshTrust`"
    responsibility: "Associates one trust domain with the CA bundles that can verify certificates from that domain."
    example: "Lets proxies verify certificates issued by the `zone1` bundled CA."
  - resource: "`MeshTLS`"
    responsibility: "Controls whether a connection must use a valid mesh identity."
    example: "`mode: Strict` rejects plaintext and untrusted certificates."
  - resource: "`MeshTrafficPermission`"
    responsibility: "Authorizes an authenticated caller after mTLS succeeds."
    example: "Allows the `flight-control` SPIFFE ID to call `check-in-api`."
{% endtable %}
<!-- vale on -->

These are separate decisions. A certificate can be valid but unauthorized, and an authorization rule cannot match a caller whose certificate is not trusted.

## Inspect the identity created in zone1

The `kong-air-identity` from the first scenario is a zone-origin resource in `{{site.mesh_namespace}}`. Its selector covers every data plane in `kong-air-mesh`, including application sidecars and mesh-scoped zone proxies.

1. Check that the identity is ready and read its resolved trust domain:

   ```sh
   kubectl get meshidentity kong-air-identity -n {{site.mesh_namespace}} \
     -o jsonpath='{.status.conditions[?(@.type=="Ready")].status}{"\n"}{.status.trustDomain}{"\n"}'
   ```

   Expected output:

   ```text
   True
   kong-air-mesh.zone1.mesh.local
   ```
   {:.no-copy-code}

   The trust domain is stored in status when the identity initializes. Omitting `spec.spiffeID.trustDomain` uses the default, `{% raw %}{{ .Mesh }}.{{ .Zone }}.mesh.local{% endraw %}`.

1. Inspect the `MeshTrust` that the Bundled provider created:

   ```sh
   kubectl get meshtrust kong-air-identity -n {{site.mesh_namespace}} \
     -o jsonpath='{.spec.trustDomain}{"\n"}{.spec.caBundles[0].type}{"\n"}'
   ```

   The trust domain matches the `MeshIdentity` status and the bundle type is `Pem`. The CA private key remains with the provider; `MeshTrust` contains only the public CA certificate needed for verification.

1. Confirm which issuer each workload uses:

   ```sh
   kubectl get dataplaneinsights -n kong-air-production \
     -o custom-columns='NAME:.metadata.name,ISSUER:.status.mTLS.issuedBackend,EXPIRES:.status.mTLS.certificateExpirationTime'
   ```

   Each `ISSUER` should contain `kong-air-identity`. An empty value means no `MeshIdentity` selector matched that data plane.

## How MeshIdentity selection works

Every `MeshIdentity` must contain `spec.selector.dataplane`. An absent selector matches no data planes. When more than one identity matches, the control plane chooses the selector with the most matching labels. If two matches are equally specific, it chooses the identity whose name sorts first.

The mesh-wide selector from the first scenario is the normal baseline:

```yaml
spec:
  selector:
    dataplane:
      matchLabels:
        kuma.io/mesh: kong-air-mesh
```

Add a more specific identity only when a group of workloads genuinely needs a different issuer, SPIFFE path, or certificate lifecycle. Do not create one identity per service merely to authorize traffic; use `MeshTrafficPermission` for authorization.

For example, an identity for `passenger-portal` would add its workload label to the existing mesh label:

```yaml
spec:
  selector:
    dataplane:
      matchLabels:
        kuma.io/mesh: kong-air-mesh
        app: passenger-portal
```

That selector is more specific than the mesh-wide selector, so it wins only for `passenger-portal`. Everything else continues to use `kong-air-identity`.

## Treat SPIFFE ID changes as a migration

The `spiffeID.trustDomain` and `spiffeID.path` fields are immutable. Changing either value moves workloads into a different identity namespace, while certificates, trust bundles, service identity status, and authorization rules update at different times.

To change the SPIFFE ID format safely:

1. Create a second `MeshIdentity` under a new name with the new trust domain or path.
1. Publish the trust required for both the old and new identities.
1. Move a small workload group by changing selectors.
1. Update `MeshTrafficPermission` rules to accept the new SPIFFE IDs.
1. Verify traffic, then migrate the remaining workloads.
1. Delete the old identity only after no workload presents its certificates.

Do not delete and recreate an identity under the same name. That removes the overlap in which both identities must remain trusted.

## Extend autogenerated identity across zones

The Bundled provider with `autogenerate.enabled: true` creates a separate CA in each zone. The generated trust domains are also zone-specific:

```text
zone1: kong-air-mesh.zone1.mesh.local
zone2: kong-air-mesh.zone2.mesh.local
```
{:.no-copy-code}

Each zone automatically trusts its own CA. KDS sends the generated zone-origin `MeshTrust` to the global control plane for visibility, but does not distribute it back down as trusted configuration for the other zones. Before cross-zone mTLS can succeed, copy each zone's generated trust into every other zone.

The resource names do not collide at the global control plane: KDS adds zone and namespace information to synced names. The explicit step is required because trust remains local, not because one zone overwrites another.

### Apply the identity in the second zone

When `zone2` is connected to the same global control plane, apply the same zone-origin identity to it. The omitted trust domain resolves to `kong-air-mesh.zone2.mesh.local` in that zone:

```sh
kubectl --context zone2 apply -f - <<'EOF'
apiVersion: kuma.io/v1alpha1
kind: MeshIdentity
metadata:
  name: kong-air-identity
  namespace: {{site.mesh_namespace}}
  labels:
    kuma.io/mesh: kong-air-mesh
    kuma.io/origin: zone
spec:
  selector:
    dataplane:
      matchLabels:
        kuma.io/mesh: kong-air-mesh
  provider:
    type: Bundled
    bundled:
      insecureAllowSelfSigned: true
      autogenerate:
        enabled: true
      meshTrustCreation: Enabled
  spiffeID:
    path: /ns/{% raw %}{{ .Namespace }}{% endraw %}/sa/{% raw %}{{ .ServiceAccount }}{% endraw %}
EOF
```

For production, prefer a managed CA or SPIRE rather than self-signed autogenerated CAs. The autogenerated configuration is used here so the trust relationship is visible and can be tested directly.

### Copy zone1 trust into zone2

Copy the public trust resource, not the CA private key. Give the copy a distinct name and remove metadata owned by the source cluster:

```sh
kubectl --context zone1 get meshtrust kong-air-identity -n {{site.mesh_namespace}} -o json | \
  jq '
    .metadata.name = "kong-air-mesh-trust-of-zone1" |
    .metadata.labels["kuma.io/origin"] = "zone" |
    del(
      .metadata.creationTimestamp,
      .metadata.generation,
      .metadata.managedFields,
      .metadata.ownerReferences,
      .metadata.resourceVersion,
      .metadata.uid,
      .metadata.labels["kuma.io/zone"],
      .status
    )' | \
  kubectl --context zone2 apply -f -
```

### Copy zone2 trust into zone1

Repeat the operation in the other direction:

```sh
kubectl --context zone2 get meshtrust kong-air-identity -n {{site.mesh_namespace}} -o json | \
  jq '
    .metadata.name = "kong-air-mesh-trust-of-zone2" |
    .metadata.labels["kuma.io/origin"] = "zone" |
    del(
      .metadata.creationTimestamp,
      .metadata.generation,
      .metadata.managedFields,
      .metadata.ownerReferences,
      .metadata.resourceVersion,
      .metadata.uid,
      .metadata.labels["kuma.io/zone"],
      .status
    )' | \
  kubectl --context zone1 apply -f -
```

For three or more zones, repeat this as an all-to-all operation: every zone needs one `MeshTrust` for every other zone whose certificates it must accept. Automate the distribution rather than maintaining an increasingly large set of manual copy commands.

## Validate trust before routing traffic

1. Confirm that each zone has its local generated trust and the copied trust from its peer:

   ```sh
   kubectl --context zone1 get meshtrust -n {{site.mesh_namespace}}
   kubectl --context zone2 get meshtrust -n {{site.mesh_namespace}}
   ```

   `zone1` should contain `kong-air-identity` and `kong-air-mesh-trust-of-zone2`. `zone2` should contain `kong-air-identity` and `kong-air-mesh-trust-of-zone1`.

1. Confirm that the copied trust domains are the peer domains:

   ```sh
   kubectl --context zone1 get meshtrust kong-air-mesh-trust-of-zone2 \
     -n {{site.mesh_namespace}} -o jsonpath='{.spec.trustDomain}{"\n"}'
   kubectl --context zone2 get meshtrust kong-air-mesh-trust-of-zone1 \
     -n {{site.mesh_namespace}} -o jsonpath='{.spec.trustDomain}{"\n"}'
   ```

   Expected output:

   ```text
   kong-air-mesh.zone2.mesh.local
   kong-air-mesh.zone1.mesh.local
   ```
   {:.no-copy-code}

These checks prove that both zones can validate the other's issuer. `MeshTLS` can now establish cross-zone mTLS; the next step is to add `MeshTrafficPermission` rules for the peer-zone SPIFFE IDs and verify an actual request through the mesh-scoped zone proxies.
