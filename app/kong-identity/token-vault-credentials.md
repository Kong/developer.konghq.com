A credential is a secret that grants access to a **third-party service**, such as GitHub or Atlassian. {{site.identity}} [Token Vault](/identity/token-vault/) stores it for a [provider](/identity/token-vault/#providers) and releases it to {{site.ai_gateway}}, so a principal (a user, an agent, or an application) can call that service without ever seeing the secret.

Token Vault stores the following credentials:

* **OAuth access and refresh tokens**: Issued by a third-party service after a user approves access. For example, the token that lets an agent open pull requests in a user's GitHub account.
* **Static access tokens**: Generated once by a third-party service, and stored by an admin for the whole directory. For example, a single GitHub personal access token used by a team.

This page covers how Token Vault encrypts, enrolls, releases, and manages these credentials.

## Credential types

The credentials can be personal or shared across the directory:

* Personal credentials: created by each user on enrollment when using a [provider OAuth template](/identity/token-vault/#providers). 
* Shared credentials: shared across the directory and managed by an admin. Can be a static value that an admin stores, or an OAuth enrollment that an admin completes once for the whole directory.

How a principal authenticates to the {{site.ai_gateway}} doesn't affect which credential type you can use. Choose the type based on the identity the authenticated actor (user or agent) should have in the third-party service:

{:.warning}
> When an admin enrolls a shared OAuth credential, every caller inherits the permissions of the account the admin signs in with. Always enroll with a dedicated service account, never with a personal account. Otherwise, callers can reach that person's private data, such as Slack direct messages or GitHub organization admin rights.

## Credential storage and encryption

Token Vault encrypts every credential before storing it, using a key that you control. Each directory has its own vault key, so one directory can't read another directory's credentials.

The following table shows what encrypts what, and what can access each key:

<!--vale off-->
{% table %}
columns:
  - title: Key
    key: key
  - title: What it does
    key: does
  - title: What has access
    key: access
rows:
  - key: "**Credential key**"
    does: |
      Generated by Token Vault (for each static secret) or {{site.ai_gateway}} (for each OAuth credential). Encrypts that credential's value.
    access: |
      Token Vault stores it only in encrypted form, protected by your vault key.
  - key: "**Vault key (public)**"
    does: |
      You register it on the directory. Protects the credential keys.
    access: |
      {{site.identity}} stores it, but can't use it to decrypt anything.
  - key: "**Vault key (private)**"
    does: |
      Unlocks a credential so it can be released.
    access: |
      Only {{site.ai_gateway_name}}. It never leaves {{site.ai_gateway_name}}.
{% endtable %}
<!--vale on-->

You need to register a vault key because it makes you the owner of the encryption: without the private key, Kong can't read your credentials. Token Vault doesn't store any credential until you register one.

A credential's value never comes back through any API. Read endpoints only return metadata (IDs, timestamps, status). Only the {{site.ai_gateway}} receives a credential, to use in outbound calls.

## Credential lifecycle

A credential moves through the following stages, depending on the action a user performs:

1. **Enrollment**: When no credentials exist yet, the first-time flow returns an enrollment URL instead of a token.
1. **Creation**: At creation, {{site.identity}} stores the credential in Token Vault. For `static_secret` providers, you generate the secret in the third-party service and store it in Token Vault yourself. For OAuth-based providers, the OAuth consent flow creates the credential and stores it automatically.
1. **Refresh**: For OAuth-based providers, {{site.ai_gateway}} refreshes credentials automatically before they expire (see the provider's `refresh_buffer_seconds`), with locking, to prevent concurrent requests from consuming a refresh token. If a refresh fails while the stored token is still valid, {{site.ai_gateway}} keeps releasing the stored token.
1. **Deletion/Revocation**: You can revoke credentials independently of the provider itself. Admins can list a user's credentials by sending a `GET` request to the [`/v2/directories/{directoryId}/principals/{principalId}/vault-credentials` endpoint](/api/konnect/kong-identity-principals/v2/#/operations/listVaultCredentials), and delete one by sending a `DELETE` request to the [`/v2/directories/{directoryId}/principals/{principalId}/vault-credentials/{vaultCredentialId}` endpoint](/api/konnect/kong-identity-principals/v2/#/operations/deleteVaultCredential). Deleting a credential doesn't delete the provider, but the user must re-enroll before an agent can call that provider on their behalf again.

## Credential enrollment

Credential enrollment is a one-time process where a user grants {{site.identity}} permission to act on their behalf with a third-party service. 
During enrollment, Token Vault creates the credential for the first time.

When you configure a provider (for example, GitHub), Token Vault registers it as a service it knows how to talk to. It doesn't mean any user has actually authorized anything yet, since there are still no credentials to hand back for Token Vault. The enrollment process follows these steps:

1. When a request comes in from the agent, {{site.ai_gateway}} returns an enrollment URL. The URL is valid for 10 minutes and opens the third-party service's OAuth consent screen. The screen lists exactly the scopes the provider requested (for example, `repo` on GitHub).
1. When the user approves, the third-party service redirects back to the {{site.ai_gateway}}'s `/_vault/callback` endpoint and sends an authorization code. The `token-vault-callback-handler` policy serves this endpoint.
1. Token Vault exchanges the authorization code for the third-party service's access token and refresh token. This exchange happens only between Token Vault and the third-party service, not through the agent.
1. {{site.ai_gateway}} encrypts the token with your directory's public vault key. Token Vault stores the encrypted token for that user and provider.

Enrollment happens once per user and per provider, not per organization.
If a second user wants to use GitHub with an agent, they need to go through enrollment, and get their own credentials stored in Token Vault. What is shared across the organization is the provider configuration (Client ID, scopes, endpoints).

For providers that support dynamic client registration (DCR), such as `atlassian-rovo`, you don't need to create an app in the provider's console: {{site.ai_gateway}} registers the OAuth client with the provider at first use.

### Shared credential enrollment

A shared credential means one credential for the whole directory, managed by an admin instead of per user. To do so, you add an OAuth provider with `credential_type` set to `shared`. Otherwise, authorization code providers default to `user` when you [add the provider](/how-to/get-started-with-token-vault/#add-a-provider).

An admin enrolls the shared credential once on behalf of the directory, with a `POST` request to the [`/v2/directories/{directoryId}/vault/providers/{providerId}/credentials` endpoint](/api/konnect/kong-identity-principals/v2/#/operations/createVaultProviderCredential). The request has no `secret`, and fails if you send one. For the variables, see [Manage credentials](#manage-credentials).

<!--vale off-->
{% konnect_api_request %}
url: /v2/directories/$DIRECTORY_ID/vault/providers/$PROVIDER_ID/credentials
status_code: 201
method: POST
headers:
  - 'Content-Type: application/json'
body_cmd: '{}'
{% endkonnect_api_request %}
<!--vale on-->

Token Vault creates a `pending` credential and returns an `enrollment_url`. Once the admin opens that URL and completes the provider's OAuth consent, the credential becomes `active` and Token Vault releases it to any authorized principal.

To release it only to some principals, include a `selector` and `priority` in the request (see [Limit credentials to specific groups](#limit-credentials-to-specific-groups)).

Use the `/v2/directories/{directoryId}/vault/providers/{providerId}/credentials/{credentialId}` endpoint for operations like:

* **Re-enrollment:** Each `GET` by credential ID returns a fresh `enrollment_url`, whether the credential is `pending` or `active`. The list endpoint never returns the `enrollment_url`.
* **Deletions:** Each `DELETE` by credential ID deletes the targeted credential. The provider stays in place, but Token Vault has nothing to release until an admin enrolls again.


## Static secret

A provider built on the `static_secret` template doesn't run an OAuth flow. The setup steps are the following:

1. You generate the credential yourself in the third-party service, for example an API key or a personal access token.
1. You store the credential on the provider.

The static credential belongs to the directory instead of to an individual principal. A `static_secret` provider only accepts `credential_type` set to `shared`.

A shared provider can hold one default credential and any number of credentials with a `selector`. 
A second credential without a selector returns a `409`. To rotate the secret, update the existing credential instead of creating another one. See [Store a credential](#store-a-credential).

## Limit credentials to specific groups

Selectors release different shared credentials to different principals, for example one API key or one OAuth enrollment per team. They apply to both kinds of shared credentials: static secrets and shared OAuth credentials. Per-user credentials don't have a selector, because each principal already has their own credential.

### Selector

`selector` is a Common Expression Language (CEL) expression (up to 1,024 characters). The expression can read these principal fields:

* `principal.id`: The principal's ID, as a string.
* `principal.display_name`: The principal's display name, as a string.
* `principal.groups`: A list of the groups the principal belongs to, directly or through a nested team. Each item is an object with an `id` key and a `type` key (`group` or `team`).
* `principal.metadata`: A map of the principal's metadata, including metadata it inherits.

Because each item in `principal.groups` is an object, match a group with `exists()` on its `id`. For example, to share credentials with a group whose ID is `7b0c9e1a-3f4d-4e2b-9a56-8d1c2f6e4b73`, you write the following CEL expression:

```
principal.groups.exists(g, g.id == "7b0c9e1a-3f4d-4e2b-9a56-8d1c2f6e4b73")
```

To share credentials with principals whose `department` metadata is `finance`, use the following expression:

```
principal.metadata.department == "finance"
```

{:.warning}
> If a metadata key contains a hyphen or another special character, use brackets instead of a dot: `principal.metadata["cost-center"] == "42"`.

The syntax follows the [CEL expressions reference](/gateway/plugins/expressions/#expression-syntax), except that `default()` isn't supported. To guard against a metadata key that might be missing, use `has()` instead:

```
has(principal.metadata.team) && principal.metadata.team == "a"
```

See [Add a selector to a credential](#add-a-selector-to-a-credential).

{{site.identity}} rejects the following expressions when you create or update the credential:

* A malformed expression
* An expression that references an unknown field
* An expression that returns a non-boolean value. For example, `principal.metadata.department` alone is rejected, but `principal.metadata.department == "finance"` is accepted
* A direct group comparison, such as `"<group-id>" in principal.groups`. Use the `exists()` form instead

### Priority

`priority` is required with a selector, and not allowed without one. Each priority must be unique on the provider, otherwise the request returns a `409`. You set `priority` with a whole number of `0` or more.

A credential without a `selector` (and therefore without a `priority`) applies to all principals.

When the {{site.ai_gateway_name}} requests a credential, Token Vault evaluates the selectors in ascending priority order and releases the first match. For example, these credentials would be checked in the following order:

1. Credential A: selector for team-a, priority 10
1. Credential B: selector for team-b, priority 20
1. Credential C: no selector (the default)

If no selector matches, it releases the default credential. If no selector matches and the provider has no default credential, Token Vault returns a `404`. Token Vault skips `pending` shared OAuth credentials, so a selector can't match until an admin completes the enrollment.

When a principal lacks the metadata key that a selector references, Token Vault treats the selector as not matching and moves on to the next credential.
For any other evaluation failure, the request fails instead of falling back to the next credential.

## Manage credentials

Make sure the directory has a [vault key](#credential-storage-and-encryption). {{site.identity}} rejects a request to store credentials with a `400` until you register one.

In the following examples, replace the following values:

* `$DIRECTORY_ID`: The ID of your directory.
* `$PROVIDER_ID`: The ID of the provider, returned when you create it.
* `$CREDENTIAL_ID`: The ID of the credential, returned when you store it.
* `$CLIENT_ID` and `$CLIENT_SECRET`: The client ID and client secret of the OAuth app you created in the third-party service.
* `$STATIC_SECRET`: The API key or token you generated in the third-party service.
* `$NEW_STATIC_SECRET`: The replacement value when you rotate a secret.
* `$GROUP_ID`: The ID of a group in your directory. To get it, send a `GET` request to the [`/v2/directories/{directoryId}/groups` endpoint](/api/konnect/kong-identity-principals/v2/#/operations/listGroups).

### Store a credential

To store a credential, create a provider, then store the credential on it. The steps depend on the provider's secret type:

Create a provider from an OAuth template, with `credential_type` set to `shared`, by sending a `POST` request to the [`/v2/directories/{directoryId}/vault/providers` endpoint](/api/konnect/kong-identity-principals/v2/#/operations/createVaultProvider).   template_name: github

### Add a selector to a credential

To limit a credential to specific groups, send a `POST` request to the [`/v2/directories/{directoryId}/vault/providers/{providerId}/credentials` endpoint](/api/konnect/kong-identity-principals/v2/#/operations/createVaultProviderCredential) with a `selector` and a `priority`:

<!--vale off-->
{% konnect_api_request %}
url: /v2/directories/$DIRECTORY_ID/vault/providers/$PROVIDER_ID/credentials
status_code: 201
method: POST
headers:
  - 'Content-Type: application/json'
body:
  secret: $STATIC_SECRET
  selector: 'principal.groups.exists(g, g.id == "$GROUP_ID")'
  priority: 10
{% endkonnect_api_request %}
<!--vale on-->

For a shared OAuth credential, omit the `secret`. Token Vault creates a `pending` credential and returns an `enrollment_url` for an admin to complete the provider's OAuth consent, as described in [Shared credential enrollment](#shared-credential-enrollment).

### List stored credentials

To list the credential metadata for a provider, send a `GET` request to the [`/v2/directories/{directoryId}/vault/providers/{providerId}/credentials` endpoint](/api/konnect/kong-identity-principals/v2/#/operations/listVaultProviderCredentials). The response contains the credential metadata (ID, `selector`, `priority`, `status`, and timestamps), never the value:

<!--vale off-->
{% konnect_api_request %}
url: /v2/directories/$DIRECTORY_ID/vault/providers/$PROVIDER_ID/credentials
status_code: 200
method: GET
{% endkonnect_api_request %}
<!--vale on-->

### Rotate a secret

To replace the stored value, send a `PUT` request to the [`/v2/directories/{directoryId}/vault/providers/{providerId}/credentials/{credentialId}` endpoint](/api/konnect/kong-identity-principals/v2/#/operations/updateVaultProviderCredential). This operation only updates an existing credential, and returns a `404` when the credential doesn't exist for this provider. The response contains the updated credential metadata, never the value:

<!--vale off-->
{% konnect_api_request %}
url: /v2/directories/$DIRECTORY_ID/vault/providers/$PROVIDER_ID/credentials/$CREDENTIAL_ID
status_code: 200
method: PUT
headers:
  - 'Content-Type: application/json'
body:
  secret: $NEW_STATIC_SECRET
  selector: 'principal.groups.exists(g, g.id == "$GROUP_ID")'
  priority: 10
{% endkonnect_api_request %}
<!--vale on-->

{:.warning}
> `PUT` replaces the whole credential, including its `selector` and `priority`. If you omit them, {{site.identity}} clears them and the credential becomes the provider's default, released to every principal that no other selector matches. Always send the current `selector` and `priority` again when you rotate a secret. To change only the selector or priority, use [`PATCH`](#update-a-selector-or-priority) instead.

For a shared OAuth credential, don't send a `secret`: the request fails if you do. `PUT` mints a fresh `enrollment_url` for an admin to re-enroll the credential, and updates the `selector` and `priority` you send.

### Update a selector or priority

To change the `selector` or `priority` of a shared credential without re-sending its secret, send a `PATCH` request to the [`/v2/directories/{directoryId}/vault/providers/{providerId}/credentials/{credentialId}` endpoint](/api/konnect/kong-identity-principals/v2/#/operations/patchVaultProviderCredential). The request only changes the fields you send, and doesn't re-enroll a shared OAuth credential:

<!--vale off-->
{% konnect_api_request %}
url: /v2/directories/$DIRECTORY_ID/vault/providers/$PROVIDER_ID/credentials/$CREDENTIAL_ID
status_code: 200
method: PATCH
headers:
  - 'Content-Type: application/json'
body:
  priority: 20
{% endkonnect_api_request %}
<!--vale on-->

* Omitted fields keep their current value.
* To remove a selector, send `selector: null`. The credential becomes the provider's default, and {{site.identity}} clears its `priority`.
* Sending a `priority` for a credential that has no selector returns a `400`.
* A `PATCH` never changes the stored secret. To replace it, use `PUT`.

### Delete a credential

To remove the stored credential, send a `DELETE` request to the [`/v2/directories/{directoryId}/vault/providers/{providerId}/credentials/{credentialId}` endpoint](/api/konnect/kong-identity-principals/v2/#/operations/deleteVaultProviderCredential):

<!--vale off-->
{% konnect_api_request %}
url: /v2/directories/$DIRECTORY_ID/vault/providers/$PROVIDER_ID/credentials/$CREDENTIAL_ID
status_code: 204
method: DELETE
{% endkonnect_api_request %}
<!--vale on-->
