`MeshIdentity` gives workloads an identity and configures the provider that supplies their
certificates. A workload presents its certificate when connecting to another proxy over mTLS.
The certificate contains a SPIFFE ID, such as
`spiffe://payments.eu.mesh.local/ns/storefront/sa/frontend`, that identifies the caller.

Three resources have distinct jobs:

| Resource | Responsibility |
| --- | --- |
| `MeshIdentity` | Select workloads and configure their identities and certificate provider. |
| [MeshTrust](/mesh/policies/meshtrust/) | Publish CA certificates that proxies use to verify peer certificates. |
| [MeshTrafficPermission](/mesh/policies/meshtrafficpermission/) | Decide whether an authenticated caller may connect to a destination. |

Issuing a certificate does not grant access. Configure the required traffic permissions before,
or alongside, enabling identities. [MeshTLS](/mesh/policies/meshtls/) controls whether a
destination also accepts plaintext and which TLS settings it uses.

A proxy that no `MeshIdentity` matches gets no identity, and therefore no mTLS. `Mesh.mtls` is
removed from the API, so this is the only way a mesh issues identities.

`MeshIdentity` is not a policy in the usual sense. It has no `targetRef`, `to` or `rules`: it
selects proxies with a label selector and describes how to issue for them. On Kubernetes it is
accepted only in the system namespace.

## Issue identities for every workload in the mesh

This example selects every proxy in the `default` mesh and uses a certificate authority (CA)
generated by the control plane. On Kubernetes, create the resource in the mesh system namespace.

{% policy_yaml %}
```yaml
type: MeshIdentity
mesh: default
name: default-identity
spec:
  selector:
    dataplane: {}
  provider:
    type: Bundled
    bundled:
      autogenerate:
        enabled: true
      insecureAllowSelfSigned: true
      meshTrustCreation: Enabled
```
{% endpolicy_yaml %}

`selector.dataplane: {}` selects every proxy in the mesh. `type: Bundled` keeps the CA in the
control plane, `autogenerate.enabled: true` creates that CA, and
`meshTrustCreation: Enabled` publishes its certificate in a `MeshTrust` so peers can verify
the identities it issues.

`insecureAllowSelfSigned: true` permits the generated self-signed CA. Peers verify its
certificates using the CA published in `MeshTrust`; the setting does not disable certificate
verification. If your organization requires certificates issued through an existing PKI,
use the supplied-CA configuration below.

## Choose which proxies an identity covers

`spec.selector.dataplane.matchLabels` picks the proxies. An empty `dataplane: {}` matches every
proxy in the mesh.

Where several identities match one proxy, the **most specific wins**: the one with the most
match labels. Where two tie on that, the one whose name sorts first alphabetically wins.

That makes a mesh-wide identity with an empty selector a base that a narrower identity overrides
— and it means adding a narrowly-scoped identity changes the trust domain of the proxies it
matches, if its trust domain differs from the one they had.

For example, an identity with `matchLabels: {app: payments}` wins over one with
`dataplane: {}` for the payments proxies. Other proxies keep the broader identity.
The two providers are not combined. Before changing a selector, check that peers trust the
chosen provider's CA and that authorization rules allow the resulting caller identity.

### A CA you supply

Leave `autogenerate` off and give `bundled.ca` a certificate and private key, each as a secure
data source. Both are required, and defining `ca` alongside `autogenerate.enabled: true` is
rejected with `shouldn't be defined once using autogenerated`.

{% policy_yaml %}
```yaml
type: MeshIdentity
mesh: default
name: corporate-ca
spec:
  selector:
    dataplane: {}
  provider:
    type: Bundled
    bundled:
      ca:
        certificate:
          type: Secret
          secretRef:
            kind: Secret
            name: mesh-ca-cert
        privateKey:
          type: Secret
          secretRef:
            kind: Secret
            name: mesh-ca-key
      certificateParameters:
        expiry: 24h
```
{% endpolicy_yaml %}

A `Bundled` provider with neither `autogenerate` nor `ca` is rejected with
`ca (): must be defined`. `certificateParameters.expiry` sets how long issued leaf certificates
last, and must not be negative.

Create the referenced secrets before applying this example. `mesh-ca-cert` supplies the
PEM CA certificate, and `mesh-ca-key` supplies its matching private key. These are signing
credentials, not an individual workload's certificate and key.

Secure data sources use different field names for each type:

| Type | Value field |
| --- | --- |
| `Secret` | `secretRef.name`, with `secretRef.kind: Secret` |
| `File` | `file.path` |
| `EnvVar` | `envVar.name` |
| `InsecureInline` | `insecureInline.value` |

The CA is loaded by the control plane, so file paths and environment variables must be available
there. Avoid embedding the private key in a policy readable by other users.

## The SPIFFE ID

`spec.spiffeID` shapes the ID issued to each workload, as Go templates. Both parts have
defaults, so most meshes leave them alone.

An ID has two parts after `spiffe://`: the trust domain and the workload path. In
`spiffe://payments.eu.mesh.local/ns/storefront/sa/frontend`, the trust domain is
`payments.eu.mesh.local` and the path is `/ns/storefront/sa/frontend`.
With the default Kubernetes template, replicas using the same namespace and service account
share an identity.

{% table %}
columns:
  - title: Field
    key: field
  - title: Variables it can use
    key: vars
rows:
  - field: "`trustDomain`"
    vars: "`.Mesh`, `.Zone`"
  - field: "`path`"
    vars: "`.TrustDomain`, `.Namespace`, `.ServiceAccount`, `.Workload`"
{% endtable %}

The defaults are:

{% raw %}
```yaml
spiffeID:
  # trustDomain, on every environment
  trustDomain: "{{ .Mesh }}.{{ .Zone }}.mesh.local"
  # path, on Kubernetes
  path: "/ns/{{ .Namespace }}/sa/{{ .ServiceAccount }}"
  # path, on Universal
  # path: "/workload/{{ .Workload }}"
```
{% endraw %}

Both fields also accept a `label` function, so `{% raw %}{{ label "team" }}{% endraw %}` reads a
label from the resource. A label that is not present fails rendering rather than resolving to an
empty string.

A template that does not parse is rejected on apply, with the Go template error attached:
`couldn't parse template: template: :1: unclosed action`.

### Change an identity without losing access

Changing the trust-domain or path template changes the identities workloads receive. The API
accepts template changes, but acceptance does not mean existing traffic will keep working.
Certificates, peer trust, and authorization rules must all agree during the transition.

The default trust-domain template includes the zone name. If that name changes, the generated
domain changes too. The control plane updates the generated `MeshTrust.spec.trustDomain` to
follow it; the domain is not pinned in `MeshIdentity` status.

For a planned change, use a second `MeshIdentity` with a distinct name so you can keep the old
issuer and its trust material while moving workloads:

1. Configure the new identity and make its CA trusted by the receiving proxies.
1. Update destination `MeshTrafficPermission` rules to allow both the old and new caller IDs.
1. Use `selector.dataplane.matchLabels` to move a small group of workloads to the new identity.
   Ensure the new selector wins according to the specificity rules above.
1. Verify the workloads' issued certificates and their calls to destinations.
1. Move the remaining workloads. Remove the old permissions and trust only after no workload
   still needs them.

Do not assume that two trusted CAs guarantee uninterrupted access: authorization rules must
also match the new IDs. Deleting and recreating an issuer can replace CA material still needed
to verify existing certificates.

## MeshTrust creation

A `Bundled` provider creates a [MeshTrust](/mesh/policies/meshtrust/) publishing its CA bundle,
which is what lets other proxies verify the certificates it issues.
`bundled.meshTrustCreation: Disabled` turns that off, for a mesh that publishes its trust
bundles some other way.

## Checking that it worked

Read the resource's status after applying it:

```sh
kubectl get meshidentity IDENTITY_NAME -n kong-mesh-system -o yaml
```

Replace the name and namespace with those used by your installation. For the autogenerated
Bundled example, expect these conditions to be `True`:

{% table %}
columns:
  - title: Condition
    key: condition
  - title: Means
    key: what
rows:
  - condition: "`Provider`"
    what: "The provider initialized — the CA was generated or loaded."
  - condition: "`MeshTrustCreated`"
    what: "The `MeshTrust` publishing the CA bundle exists."
  - condition: "`Ready`"
    what: "The identity is initialized and issuing."
{% endtable %}

For an automatically generated trust resource, read `MeshTrust.spec.trustDomain` to see the
domain it currently publishes. Confirm the identity actually issued to a workload by inspecting
the SPIFFE URI in that workload's certificate.

`MeshTrustCreated` is only reported when the provider publishes a CA for automatic trust
creation. Its absence is not itself a failure when trust is managed separately. Read the
`reason` and `message` of a false condition for the failed initialization step.

A resource with no `provider` operates in SPIFFE-ID-only mode: it advertises service
identities without issuing workload certificates. Its status reports `SpiffeIDProvider: True`
and `Ready: False` with reason `PartiallyReady`. Do not treat that status as proof of mTLS.

Finally, inspect a selected proxy's workload certificate through Envoy's `/certs` admin
endpoint. Confirm that its SPIFFE URI matches the expected trust domain and path, then make an
authorized mTLS request to a peer. A ready resource confirms initialization; this request checks
certificate delivery, peer trust, and permission together.
