`MeshIdentity` gives a workload a SPIFFE ID and the certificate that proves it. Everything in
the mesh that depends on knowing who a workload is depends on this: mTLS between proxies,
[MeshTrafficPermission](/mesh/policies/meshtrafficpermission/) rules matching on `spiffeID`, and
the `Strict` inbounds that [MeshTLS](/mesh/policies/meshtls/) configures.

A proxy that no `MeshIdentity` matches gets no identity, and therefore no mTLS. `Mesh.mtls` is
removed from the API, so this is the only way a mesh issues identities.

`MeshIdentity` is not a policy in the usual sense. It has no `targetRef`, `to` or `rules`: it
selects proxies with a label selector and describes how to issue for them. On Kubernetes it is
accepted only in the system namespace.

## Issue identities for every workload in the mesh

This resource matches every proxy and issues from a CA the control plane generates itself:

{% policy_yaml %}
```yaml
type: MeshIdentity
mesh: default
name: default-identity
spec:
  selector:
    dataplane: {}
  provider:
    type: Bundled
    bundled:
      autogenerate:
        enabled: true
      insecureAllowSelfSigned: true
      meshTrustCreation: Enabled
```
{% endpolicy_yaml %}

`insecureAllowSelfSigned` is required to accept a self-signed CA, and the name says what it
costs: nothing outside the mesh verifies that CA. It suits a demo or a first deployment, not a
production mesh.

## Choose which proxies an identity covers

`spec.selector.dataplane.matchLabels` picks the proxies. An empty `dataplane: {}` matches every
proxy in the mesh.

Where several identities match one proxy, the **most specific wins**: the one with the most
match labels. Where two tie on that, the one whose name sorts first alphabetically wins.

That makes a mesh-wide identity with an empty selector a base that a narrower identity overrides
— and it means adding a narrowly-scoped identity changes the trust domain of the proxies it
matches, if its trust domain differs from the one they had.

## Providers

`spec.provider.type` chooses where certificates come from.

### A CA you supply

Leave `autogenerate` off and give `bundled.ca` a certificate and private key, each as a secure
data source. Both are required, and defining `ca` alongside `autogenerate.enabled: true` is
rejected with `shouldn't be defined once using autogenerated`.

{% policy_yaml %}
```yaml
type: MeshIdentity
mesh: default
name: corporate-ca
spec:
  selector:
    dataplane: {}
  provider:
    type: Bundled
    bundled:
      ca:
        certificate:
          type: Secret
          secretRef:
            kind: Secret
            name: mesh-ca-cert
        privateKey:
          type: Secret
          secretRef:
            kind: Secret
            name: mesh-ca-key
      certificateParameters:
        expiry: 24h
```
{% endpolicy_yaml %}

A `Bundled` provider with neither `autogenerate` nor `ca` is rejected with
`ca (): must be defined`. `certificateParameters.expiry` sets how long issued leaf certificates
last, and must not be negative.

The certificate and key take the same secure data source shape used elsewhere: a `type` of
`Secret`, `File`, `EnvVar` or `InsecureInline`, with the value under a field of the same name.

## The SPIFFE ID

`spec.spiffeID` shapes the ID issued to each workload, as Go templates. Both parts have
defaults, so most meshes leave them alone.

{% table %}
columns:
  - title: Field
    key: field
  - title: Variables it can use
    key: vars
rows:
  - field: "`trustDomain`"
    vars: "`.Mesh`, `.Zone`"
  - field: "`path`"
    vars: "`.TrustDomain`, `.Namespace`, `.ServiceAccount`, `.Workload`"
{% endtable %}

The defaults are:

{% raw %}
```yaml
spiffeID:
  # trustDomain, on every environment
  trustDomain: "{{ .Mesh }}.{{ .Zone }}.mesh.local"
  # path, on Kubernetes
  path: "/ns/{{ .Namespace }}/sa/{{ .ServiceAccount }}"
  # path, on Universal
  # path: "/workload/{{ .Workload }}"
```
{% endraw %}

Both fields also accept a `label` function, so `{% raw %}{{ label "team" }}{% endraw %}` reads a
label from the resource. A label that is not present fails rendering rather than resolving to an
empty string.

A template that does not parse is rejected on apply, with the Go template error attached:
`couldn't parse template: template: :1: unclosed action`.

### The trust domain is pinned once

The control plane renders `trustDomain` the first time it initializes the identity and records
the result in `status.trustDomain`, then keeps issuing in that value.

A template referencing something that can move, such as `{% raw %}{{ .Zone }}{% endraw %}` on a zone that is
later renamed, therefore keeps resolving to the domain the published `MeshTrust` advertises.
Without the pin, renaming a zone would move every workload into a trust domain no `MeshTrust`
had published yet.

### Changing it is a migration, not an edit

`spiffeID.trustDomain` and `spiffeID.path` are **immutable**. An update changing either is
rejected with `is immutable, cannot be changed from "..." to "...". Create a MeshIdentity under
a different name with the new value and delete this one once every workload has migrated`.

The reason is that the pieces move on different schedules. Issuance would re-render at once,
while the `MeshTrust` publishing the CA bundle, `MeshService.spec.identities`, and the
`spiffeID` rules in `MeshTrafficPermission` all catch up separately, leaving already-issued
certificates unverifiable in between.

To move a trust domain, create a second `MeshIdentity` **under a different name**, and delete
the old one once every workload has been issued from the new one. Both publish their own
`MeshTrust` and `MeshService.spec.identities` lists every matching identity's SPIFFE ID, so
peers accept certificates from both for the whole transition. Steer which identity a workload
picks with `selector.dataplane.matchLabels` while both exist.

Deleting and recreating under the *same* name is accepted and does converge, but it is not a
migration: the `MeshTrust` and the CA are keyed by the identity's name, so for as long as
convergence takes there is one trust domain in flight and certificates issued under the old one
no longer verify.

## MeshTrust creation

A `Bundled` provider creates a [MeshTrust](/mesh/policies/meshtrust/) publishing its CA bundle,
which is what lets other proxies verify the certificates it issues.
`bundled.meshTrustCreation: Disabled` turns that off, for a mesh that publishes its trust
bundles some other way.

## Checking that it worked

`status.conditions` reports three things, and all three are `True` on a working identity:

{% table %}
columns:
  - title: Condition
    key: condition
  - title: Means
    key: what
rows:
  - condition: "`Provider`"
    what: "The provider initialized — the CA was generated or loaded."
  - condition: "`MeshTrustCreated`"
    what: "The `MeshTrust` publishing the CA bundle exists."
  - condition: "`Ready`"
    what: "The identity is initialized and issuing."
{% endtable %}

`status.trustDomain` shows the value issuance is pinned to, which is the one to compare against
a `MeshTrust` or a `MeshTrafficPermission` rule when identities are not verifying.
