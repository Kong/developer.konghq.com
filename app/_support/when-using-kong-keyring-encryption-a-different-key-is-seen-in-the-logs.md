## When using Kong Keyring encryption a different key is seen in the logs

When using Keyring encryption, the private and public key are provided via parameters;

```bash
KONG_KEYRING_PUBLIC_KEY=/tmp/keyring_public.pem
KONG_KEYRING_PRIVATE_KEY=/tmp/keyring_private.pem
KONG_KEYRING_ENABLED=on
KONG_KEYRING_STRATEGY=cluster
```

But a different public key is seen in the log. Where does this different key come from?

The Kong keyring keypair is not used to generate the keyring data. These parameters define a keypair to be used for encryption/decryption when exporting/importing the keyring.

At a high level, there are two sets of keys that are used for the keyring;

- an ephemeral key pair is generated by Kong and this key is used to generate the keyring content (this is the public key seen in the log). This is totally different from the Kong keyring parameters and there is no end user configuration for this key pair
- the `keyring_public_key` and `keyring_private_key` are referred to as the keyring "Management RSA Key Pair". These management keys are used to encrypt/decrypt the keyring when using the export/import endpoints

When a Kong instance is stopped, the current keyring information is "lost" as it is only stored in memory. If only a single kong node in a cluster goes down, when it restarts it will broadcast and get the current keyring data. If all the Kong nodes are stopped simultaneously, then the keyring data is lost.

For this reason it is critical that you keep secure copies of both the keyring data generated by Kong and the "Management RSA Key" pair. The keyring must be reimported when the Kong instance is restarted. Without this keyring data, it will no longer be possible to decrypt the encrypted items.
